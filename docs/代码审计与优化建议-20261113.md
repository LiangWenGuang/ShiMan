# ShiMan 代码审查与优化方案（2026-11-13）

## 1. 审查范围与边界

- 仓库：`LiangWenGuang/ShiMan`，基线 `main@79198eb9866c8346ec8f55a137b54046bd4b8e83`。
- 关注：`net/Http.ets`、`source/SourceApi.ets`、`pages/SourceSwitchPage.ets`、`pages/SourceManagerPage.ets`、`store/Library.ets`、`util/Text.ets`、图源配置和离线测试工具。
- 本轮是**重点路径静态审查 + 针对性修复**，不是所有页面、所有外部图源的穷尽性审计。
- 本次操作不具备 DevEco/HarmonyOS 真机运行环境，也未对外部漫画站点执行在线全链路验证。不要把“代码已修正”解释为“真机已验证”。
- `sources/index.json` 当前列出 19 个配置。历史 README 的 6 个可完整阅读源是历史验证结论，不代表此刻全部可用。

## 2. 已修复缺陷

| 优先级 | 文件 | 缺陷与触发条件 | 改动 |
| --- | --- | --- | --- |
| P0 | `net/Http.ets` | 首次请求限制 8 MiB，GET 异常重试却未检查响应大小；大页面在重试后可绕过保护。 | 重试分支和字符串分支统一校验体积，避免解码超大响应。 |
| P1 | `store/Library.ets` | 快速滚动时，多次 `Preferences.put(progress)` 异步并行，旧快照可能晚于新快照落盘。 | 串行写入、脏标记合并，只持久化最新快照。 |
| P1 | `pages/SourceSwitchPage.ets` | 换源将所有图源搜索和详情请求一次性 `Promise.all`，图源数量增多时瞬间并发。 | 两阶段各最多 3 个工作协程；离开页面后废弃旧结果，单源异常不阻断其他源。 |
| P1 | `util/Text.ets` | `allCapturesOf` 对零宽全局正则无游标推进，可能无限循环。 | 零宽匹配推进游标，并限定最大处理次数。 |
| P1 | `source/SourceApi.ets` | 目录 JSON 接口 HTTP 200，但内容变化导致解析为空时，直接出现“未解析到章节”。 | 对空结果增加详情 HTML 目录兜底。 |
| P2 | `source/SourceApi.ets` | `images.url` 为相对地址时直接发送 HTTP 或交给 Web 组件。 | 基于章节页地址归一化为绝对 URL。 |
| P2 | `net/Http.ets` | User-Agent 的 `AppleWebKit` 被误写成 `AppleWeb statKit`，可能影响服务器识别。 | 修正为标准 `AppleWebKit/537.36`。 |
| P2 | `net/Http.ets` | 图片 403/404 和超大响应也会无意义地再请求一次。 | 只在网络异常、408、429、5xx 时尝试重试。 |
| P2 | `pages/SourceManagerPage.ets` | 自检抛异常后加载指示可能无法结束；“可访问但无搜索结果”被显示为“不可用”。 | 加入防重复、自检完成清理，并将“站点可访问但解析待确认”单独标识。 |
| P2 | `store/Library.ets` | 部分偏好写入链未等待 `flush()`，可能出现未处理的异步异常。 | 通过 `await` 将刷新异常纳入原来的 catch。 |
| P2 | `tools/prepare-engine-test.mjs`、`tools/sync-engine-tests.sh` | 脚本绑定旧开发电脑 `F:` 盘绝对路径。 | 改成按脚本所在目录定位仓库。 |

## 3. 自动化回归

新增 GitHub Actions 工作流 `.github/workflows/engine-regression.yml`：

- `node --experimental-transform-types tools/engine-test/run.ts`：测试实际 `.ets` 源码镜像中的 HTML/JSON、URL 解析和零宽正则等。
- `node --experimental-transform-types tools/engine-test/runtime.ts`：用无网络、无鸿蒙 SDK 的模拟依赖测试 HTTP 重试体积限制、404 不重试、网络错误重试，以及同一阅读进度键的串行写入和最终值。
- CI 成功不替代 DevEco 编译与真机回归，尤其不能证明第三方站点当前可用。

## 4. 仍需处理的风险与优化计划

### P1 — 首先推进

1. **建立图源质量基线。** 对 19 个内置配置逐一验证“搜索、详情、目录、正文首图/多图、封面 Referer”，记录站点、样本、时间和失败阶段。腾讯动漫正文仍是已知历史限制；不应仅凭首页可访问就宣称可完整阅读。
   - 验收：每个启用图源都有最近一次五阶段结果；默认启用策略仅依赖明确验证的能力。
2. **补全真机回归。** 在 HarmonyOS 7/目标 API 设备上执行：弱网/超时、连续快速切章、书架继续阅读、返回应用、跨源换源、滚动恢复、多图片长章节。
   - 验收：无闪退、阅读进度最终保存最新位置，图片请求并发与内存峰值有可复核记录。
3. **给网络请求引入可取消的任务上下文。** 目前通过 token 忽略旧结果，但在飞行中的 HTTP 请求仍可能持续占用连接直至超时。优先验证 ArkTS 官方 API 的请求取消支持，再把取消与页生命周期联动。
   - 验收：离开搜索/换源/阅读页面后，过期任务不再继续占用大量下载配额。

### P2 — 第二阶段

4. **图源健康评分。** `SourceHealth` 目前仅保存进程内最后结果，建议按“连通、解析、章节、正文图片”分维度统计成功率、最近成功时间及失败样本；展示时间戳并设置过期状态。
5. **图片缓存与内存监控。** `ImageLoader` 仅按 URL 缓存字节、默认 24 MiB 上限和并发 4；长图解码后 PixelMap 的实际内存可能远高于原图大小。加入分辨率采样、失败记录上限、按图片类型/用途的缓存策略，并测量真机 PSS/解码峰值。
6. **完善换源章节匹配。** 当前按章节数字或位置兜底，容易把“序章/番外/合并章节/重排章节”对齐错。增加标题规范化、分卷识别、置信度与用户手动确认。
7. **减少 UI 与业务逻辑耦合。** `Index.ets` 超过 60 KB、`ReaderPage.ets` 约 40 KB。将搜索状态机、阅读恢复、Web 取图与 UI 视图拆分到可独立测试模块。
8. **扩展异常路径自动化测试。** 增加 SourceApi 的 JSON 空目录兜底、图片 URL 相对路径、换源并发上限、损坏 JSON、无效字符编码与乱序请求回调的测试。

### P3 — 日常维护

9. **清理历史探测脚本中的绝对路径。** 本次修复主同步脚本；`tools/engine-test` 仍有历史探测脚本直接引用旧 `F:` 目录，建议统一使用 `import.meta.dirname` 或传入 CLI 路径。
10. **统一版本与文档。** README 中历史产物、图源数与运行状态易随发布变旧。使用统一版本来源生成发布说明，将“配置数量、历史验证、当前健康状态”分开描述。
11. **代码质量门禁。** 固定 Node/DevEco 版本；对纯逻辑模块跑回归、对 ArkTS 工程跑编译、对发布包跑签名与安装检查。PR 未通过关键检查前不要自动合并。

## 5. 建议验收顺序

先执行本 PR 离线 CI → DevEco 编译签名 HAP → HarmonyOS 7 真机阅读/换源/进度测试 → 19 源当前可用性探测 → 再进行缓存与架构重构。对未经外部站点验证的能力一律标注“待验证”，避免将“HTTP 成功”与“漫画可读”混淆。
