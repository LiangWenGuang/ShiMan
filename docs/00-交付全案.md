### 1.2 平台选型结论

选 **HarmonyOS 原生 ArkTS**，不选 Web/PWA/Flutter：

- Web/PWA 无法获得系统级图片解码与手势体验，长条漫滚动会掉帧；
- Flutter 在鸿蒙上是移植层，包体大、系统能力接入绕；
- 原生可用系统 `Image` 组件直接吃网络图（带磁盘缓存），阅读器性能最好；
- 系统 `Web` 组件提供了「无头取图」这条关键后路（见 1.4）。

### 1.3 ★ 图源生态现状（本项目的真正难点）

原方案（VenHM 魔改）靠内嵌 QuickJS 跑 141 个 Legado 转换源。这次要求「完全自研运行时」，等于放弃 JS 执行能力。所以第一步不是写代码，而是**搞清楚在纯 HTTP 条件下到底能拿到什么**。

11 轮探测、31 个候选站点，结论如下：

| 站点 | 搜索 | 详情 | 章节 | 图片 | 判定 |
|---|---|---|---|---|---|
| **漫客栈 mkzhan.com** | ✅ HTML | ✅ HTML | ✅ HTML | ✅ **JSON 接口** | **完全可用** |
| 腾讯动漫 m.ac.qq.com | ✅ HTML | ✅ HTML | ✅ 内嵌 JSON | ⚠️ 需执行页面 JS | 可用（需无头取图） |
| 极速漫画 m.1kkk.com | ✅ HTML | ✅ HTML | ❌ JS 加载 | ❌ JS 注入 | 不可用 |
| 动漫屋 m.dm5.com | ✅ HTML | ✅ HTML | ❌ JS 加载 | ❌ JS 注入 | 不可用 |
| 包子漫画 baozimh.org | ✅ HTML | ✅ HTML | ✅ JSON 接口 | ❌ 区域限制 404 | 不可用 |
| 拷贝漫画 / 动漫之家 | ❌ DNS / 连接重置 | — | — | — | 不可达 |
| 哔哩哔哩漫画 | ❌ 需客户端签名 | — | — | — | 不可用 |
| MangaDex | ❌ Cloudflare 挑战 | — | — | — | 不可用 |
| 亲亲漫画 | 可达但为成人站 | — | — | — | **主动排除** |

**核心事实：中文漫画站几乎全部把章节图片藏在页面 JS 之后。** 这是反爬的行业惯例，不是个别现象。

### 1.4 关键架构决策

面对这个事实有三条路，我选第三条：

| 方案 | 结果 | 取舍 |
|---|---|---|
| A. 只做 HTTP 可解的源 | 只有漫客栈 1 个源 | 满足不了「多源」 |
| B. 重新引入 JS 引擎 | 能大量兼容 | 违背「完全自研运行时」 |
| **C. 系统 Web 组件无头取图** | 覆盖 JS 注入型站点 | **选它**。零第三方依赖，纯系统能力 |

具体做法：章节目录仍走 HTTP（快），只有图片列表交给一个 1×1 的隐藏 `Web` 组件去渲染目标页，`onPageEnd` 后注入脚本把 `<img>` 的 `data-src` 捞回来。用户看到的是加载遮罩，感知成本约 1~2 秒。

### 1.5 平台兼容性

本机 SDK 只有 API 22（HarmonyOS 6.0.2）。应用以 API 22 编译、`compatibleSdkVersion` 同为 22，**在鸿蒙 7.0 设备上可直接安装运行**（系统向后兼容低版本 API）。不使用任何 7.0 独占 API，因此不存在「只有 7.0 能跑」的风险。

## Phase 1c · 技术研发方案

### 分层

```
pages/      6 个页面（ArkUI）
   ↓
source/     SourceRegistry（注册表） · SourceApi（门面）
   ↓
rule/       Rules（DSL 模型） · Engine（执行器）
   ↓
parse/      Html（分词器 + DOM 树） · Selector（CSS 引擎） · Json（解析 + JSON Path）
   ↓
net/        Http（编码探测 / 幂等重试 / 体积闸门）
   ↓
store/      Library（书架 / 进度 / 历史）
```

### 自研组件规模

| 模块 | 职责 | 关键实现要点 |
|---|---|---|
| `parse/Html` | HTML → DOM 树 | 手写分词器；script/style 原样吞掉；未闭合标签用栈补齐；节点数上限 6 万防打爆内存 |
| `parse/Selector` | CSS 选择器 | 支持标签/id/class/属性（=/`*=`/`^=`/`$=`）/后代/子代/相邻/兄弟/`:nth-child`/`:contains`；从右向左回溯匹配 |
| `parse/Json` | JSON 解析 + Path | 不用 `JSON.parse`（ArkTS 动态键访问类型不安全），自己产出强类型节点树，顺带支持 JSONP 外壳 |
| `rule/Engine` | 规则执行 | FieldExpr 求值、备选链、正则后处理、列表/详情/章节/图片四类解析器 |
| `net/Http` | 请求层 | 取字节流自己按 charset 解码；非幂等请求不重试；响应体上限 8 MB |

### 三个工程决策及其理由

1. **为什么自己写 JSON 解析**：ArkTS 严格模式下 `JSON.parse` 返回 `Object`，动态键访问要反复强转，既啰嗦又容易在运行时炸。自研解析器一次搞定，还能顺手兼容站点的 JSONP 包裹。

2. **为什么图片地址统一升级 HTTPS**：鸿蒙默认拦截明文 HTTP，而漫客栈图片接口返回的是 `http://content.mkzcdn.com/...`。实测该 CDN 的 https 返回与 http 完全一致（同样 139495 字节），所以在解析层统一 `http → https`，比配网络安全策略更省事、更可靠。

3. **为什么章节窗口化而不是 LazyForEach**：详情页是 `Scroll > Column` 整体滚动，塞 `LazyForEach` 会变成嵌套滚动。改用「窗口 120 话 + 显示更多」渐进展开，规避嵌套滚动的同时保证千章不卡。

### 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 腾讯源无头取图失败 | 少一个可用源 | 阅读器给「换源」兜底；规则可热改 |
| 站点改版 | 规则失效 | 规则是纯 JSON，改文件即修，不用重新编译引擎 |
| 换源章节错位 | 用户跳到错误章节 | 三级对齐：章节号 → 索引夹取 → 提示实际落点 |
| 无真机验证 | UI 可能有布局问题 | 已把验证清单一并交付，用户 5 分钟可过一遍 |

## Phase 3 · 上线发布

### 发布形态

本项目为**个人使用工具**，不走应用市场（漫画聚合类应用在华为应用市场基本无法过审，涉及内容授权）。发布方式为本地装机。

### 版本策略

| 版本 | 内容 |
|---|---|
| 1.0.0（本次） | 双源、发现/搜索/书架/详情/阅读/换源、竖向阅读 |
| 1.1.0 | 横向翻页 + 双页模式；离线下载队列 |
| 1.2.0 | 图源规则在线导入/编辑；源健康统计与自动排序 |
| 2.0.0 | 多平台源（含国际源）；聚合搜索去重 |

### 回滚预案

工程无服务端，回滚 = 装回上一版 HAP。建议每次装机前保留上一版 `hap/` 产物（已按时间戳命名，天然支持回滚）。

### 审核风险提示

- 若未来尝试上架：需提供每个图源的授权证明，否则必然因「侵犯著作权」被拒；
- 应用描述中避免出现「免费看全网漫画」等表述；
- 建议定位为「本地漫画阅读器 + 可自定义规则」，而不是「盗版聚合」。

## Phase 5 · 运营增长

本项目是个人工具，运营目标不是拉新，而是**让图源长期可用**。

### 源扩充路线（按可行性排序）

| 优先级 | 方向 | 依据 |
|---|---|---|
| P0 | 给腾讯源做真机调优 | 结构已确认，只差无头取图的 selector 微调 |
| P1 | 复检极速/动漫屋的章节接口 | 已确认站点可达，章节接口尚未逆向成功，值得再挖一轮 |

## 遗留问题清单（诚实版）

1. **腾讯动漫正文图片取不到** —— 搜索、详情、1378 话目录在真机上均正常，但正文图不在页面 DOM 里（只暴露 1 张分享图），无头取图对它无效。需要逆向 `m.ac.qq.com` 的章节接口。当前阅读时会提示「该图源未能提取到正文图片，可尝试换源」，不会白屏也不会崩。
2. **阅读器功能偏薄** —— 只有竖向连续，没有横向翻页、双页、卷轴、亮度/翻页动效。
3. **没有离线下载** —— 依赖系统 Image 缓存，清缓存后需重新加载。
4. **签名 365 天到期** —— 2027-11-01 失效，届时需重新签名；证书同时到期会换新，覆盖安装不了，须先卸载（书架与进度会丢）。
5. **无源健康持久化** —— 只有手动「连通性自检」。
